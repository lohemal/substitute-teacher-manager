작성일: 2026-09-04 / 검토 완료 후 구현 착수

> **실제 스키마의 원본은 `src-tauri/migrations/001_init.sql`입니다.**
> 이 문서는 설계 의도를 설명하며, 아래 항목은 검토 결과를 반영해 문서보다 확장되었습니다.
>
> | 항목 | 반영 내용 |
> |---|---|
> | `terms` | `school_year`, `semester`, `is_current` 추가. 최초 설정에서 현재 학년도·학기를 지정하고, 이후 화면은 현재 학기만 다룸. 이전 학기 보결 기록은 삭제하지 않고 조회 가능 |
> | `lessons` | `lesson_type`(SPECIAL/CROSS/CO/ETC)과 `replaces_homeroom` 추가. **공동수업은 담임도 함께 들어가므로 `replaces_homeroom=0`** — 담임 시간표 계산에서 제외하지 않음 |
> | `teacher_busy_blocks` | `block_type`(DUTY 고정업무 / NO_SUB 보결 배정 불가 / OTHER) 추가 |
> | `absences` | 종일·일부 시간 부재를 모두 표현(`is_all_day`, `start_min`, `end_min`) + CHECK 제약 |
> | `substitutions` | 같은 교사 이중 배정, 같은 학급 이중 보결을 막는 부분 유니크 인덱스 2개 추가 |
> | 조회 결과 | `TargetSlot.in_charge`(이 시간을 원래 담당하는 교사) + `FindResult.notice` 추가. **그 시간에 전담이 들어오면 담임이 결근해도 보결이 필요 없으므로** "전담(과목) 시간입니다. 확인 바랍니다." 안내를 조회 전·후에 띄워 헛배정을 막음. 전담 본인이 결근한 경우에는 안내하지 않음 |
> | 배정 (Phase 8) | 스키마 변경 없이 001/002의 컬럼을 그대로 쓴다. 저장 값은 모두 **그 시점 스냅샷** — `term_id`·`date`·`day_of_week`·`grade`·`class_id`·`class_label`·`slot_type`·`period_no`·`slot_label`·`start_min`·`end_min`·`absent_teacher_id`·`sub_teacher_id`·`subject_id`·`reason_code`·`status`·`created_at`·`cancelled_at`·`cancel_reason`. 취소는 `status='CANCELLED'`로만 바꾸고 행은 지우지 않는다 |
> | 교사명 스냅샷 | **넣지 않기로 했다.** Phase 4에서 보결 기록이 있는 교사는 삭제가 막히고 비활성만 되므로 `teacher_id`가 항상 풀린다. 이름이 바뀌는 경우는 대부분 오타 수정·개명이라 과거 기록도 새 이름으로 보이는 편이 옳다. 반 이름은 반대다 — 학년마다 새로 붙는 값이므로 `class_label`로 고정한다 |
> | 겹침 방지 | 부분 유니크 인덱스는 **같은 시작 시각**만 막는다. SQLite로 구간 겹침을 제약할 수 없으므로 쓰기 트랜잭션 안에서 `domain::assign::verify`(조회와 같은 엔진) + `guard_overlap`(SQL 구간 질의)으로 확인한다. 일괄 배정은 한 칸을 확정할 때마다 `occupy`로 하루치 자료에 반영해 다음 칸을 검증하므로, 같은 교사를 연속 교시에 넣는 것은 되고 같은 시각 두 반에 넣는 것은 막힌다 |
> | 중간놀이 | **보결을 배정하지 않는다.** 현장에서 그 시간까지 사람을 넣지는 않기 때문이다. 다만 후보 판정에서는 여전히 담임의 '바쁜 시간'이므로, 중간놀이 중인 선생님을 다른 반 보결로 부르지는 않는다 |
> | 다건 배정 화면 | 같은 선생님이 한 반의 여러 교시에 들어가는 것은 현장에서 흔하므로 **막지도, 자동으로 다음 순위로 넘기지도 않는다.** 각 칸은 늘 추천 1순위를 골라 두고, 같은 분이 두 곳 이상이면 상태 칸에 연한 빨강 `중복`으로만 표시한다. 시각까지 겹치면 저장이 불가능하므로 `시각 겹침`으로 따로 구분하고 [배정]을 잠근다 |
> | 현황 (Phase 9) | **집계표를 두지 않는다.** 모든 숫자는 조회할 때마다 `substitutions`·`absences`를 다시 세어 만든다. 그래서 배정을 취소하거나 고치면 곧바로 반영되고, 어긋날 여지가 없다 |
> | '보결 필요' 계산 | 등록된 결근에서 `domain::assign::duty_slots`로 뽑는다 — 다건 배정 화면과 **같은 계산**이라 두 화면의 숫자가 어긋나지 않는다. 결근이 없는 날은 건너뛰므로 한 달치를 봐도 실제로 읽는 날은 몇 날뿐이다. `required = covered + unassigned`는 항상 성립하지만, `assigned`(기간 안 배정 건수 전체)는 결근 등록 없이 배정한 건을 포함하므로 `covered`보다 클 수 있다 |
> | 공정성 표시 | `domain::fairness`. **같은 구분(담임·전담·기타)끼리만** 견주고, 평균에서 2회 또는 평균의 25% 가운데 큰 폭을 벗어날 때만 `평균보다 많음/적음`을 붙인다. 구분 안에 3명 미만이거나 모두 같으면 표시하지 않는다. '과다·문제' 같은 판정 문구는 쓰지 않고 색도 경고색을 피한다 |
> | 백업 · 복원 (Phase 10) | 파일을 복사하지 않고 **SQLite 백업 API**를 쓴다 — WAL에만 있는 내용까지 담기고 쓰는 도중에도 안전하다. 복원은 ① 지금 자료를 `before-restore-…`로 백업 → ② 연결을 닫고 → ③ 백업 내용을 자료 파일로 옮기고 → ④ 다시 열며 마이그레이션 적용. 어느 단계에서 실패해도 ①로 되돌아간다. 파일은 열어서 스키마 버전과 필수 표를 확인한 뒤에만 복원한다 |
> | 자동 백업 | `OFF / DAILY / ON_EXIT`, 기본 DAILY·10개 보관. **자동 백업만** 개수를 지켜 지우고 직접 만든 백업(`보결자료-…`)과 안전 백업(`before-…`)은 건드리지 않는다 |
> | 동작 옵션 | `repo::settings::ENGINE_OPTIONS` 한 곳에만 정의한다 (화면은 이 목록을 보고 그린다). 새 옵션은 여기 한 줄 + `EngineSettings` 한 필드. **시간 충돌을 끄는 옵션은 만들지 않는다** — 방침이 아니라 사실의 문제이고, 끄는 순간 한 사람이 같은 시각에 두 교실에 있게 된다 |
> | 새 학기 | `terms` 행을 새로 만들고 학급·시정표·전담 수업을 **선택적으로 복사**한다. 교사·과목은 term_id가 없어 학교에 속하므로 복사할 것이 없다. 지난 학기 자료는 손대지 않으며, 보결 기록은 `class_label`·시각 스냅샷 덕분에 새 학기에 반 이름이 바뀌어도 그대로다 |
> | CSV | UTF-8 **BOM**(`EF BB BF`) + CRLF. 이 세 바이트가 없으면 Windows Excel에서 한글이 전부 깨진다. 화면에 걸린 기간·필터를 그대로 넘겨 내보낸다 |
> | 초기화 | 동작 옵션 초기화(자료 유지)와 자료 전체 초기화를 완전히 분리했다. 후자는 `전체 초기화` 문구를 그대로 입력해야 하고, 지우기 직전에 반드시 백업을 남긴다 |
> | 업데이트 (Phase 11) | Tauri Updater + GitHub Releases. 앱 안에 **공개 키**가 박혀 있고, 개인 키로 서명된 파일만 설치한다. 확인 → 내려받기 → 다시 시작을 모두 사람이 누르게 한다 (업무 중 갑자기 다시 켜지면 안 된다). 개인 키는 저장소 밖(`%USERPROFILE%.bogyeol-release`)에 두고 GitHub Secret 으로만 CI에 넘긴다. 자세한 절차는 `docs/02-배포.md` |
> | 버전 | `package.json`·`tauri.conf.json`·`Cargo.toml` 세 곳이 같아야 업데이터가 새 버전을 알아본다. 손으로 고치지 않고 `npm run version:set 0.2.0` 을 쓴다 |
>
> 예외 일정(교차수업·공동수업·고정업무·보결 불가·기타 정기 일정)은 **등록하지 않으면 아무 영향이 없습니다.**
> 일반 학교는 전담 시간표만 입력하면 되고, 필요한 학교만 예외를 추가합니다.

## 0. 요구사항 검토 의견 (먼저 확인이 필요한 부분)

설계에 앞서, 요구사항을 그대로 구현했을 때 문제가 되거나 크게 개선할 수 있는 지점입니다.

### (1) 담임 시간표는 입력받지 않고 "파생"시킨다 — 가장 중요한 결정

요구사항에는 전담교사 시간표만 입력하도록 되어 있습니다. 그렇다면 담임교사가 언제 수업 중인지는
어떻게 아는가? 답은 **초등학교 구조상 계산이 가능하다**는 것입니다.

> 담임의 수업 시간 = (자기 반의 그 요일 전체 교시) − (그 반에 전담이 들어오는 교시)

즉 5-2반 수요일에 1~6교시가 있고 3교시에 전담 영어가 들어온다면,
5-2 담임은 1, 2, 4, 5, 6교시 수업 / 3교시 공강입니다.

이 방식의 장점:

- 담임 20여 명의 시간표를 일일이 입력할 필요가 없음 → 초기 설정 시간이 크게 줄어듦
- 전담 시간표만 정확하면 전체가 정확해짐 (입력 지점이 하나 = 오류 지점이 하나)
- 전담 시간표를 수정하면 담임 공강이 자동으로 따라 바뀜

예외 처리:

- 담임이 다른 반 수업에 들어가는 경우(교과 교차 지도) → 담임도 전담과 동일한 테이블에
  행을 추가할 수 있게 함 (테이블명을 `lessons`로 두고 교사 구분과 무관하게 사용)
- 특정 교사의 고정 업무(순회, 협의회 등) → `teacher_busy_blocks`로 별도 등록

**설정에서 `담임 시간표 자동 계산` 옵션을 켜고 끌 수 있게 하되, 기본값은 켜짐으로 합니다.**

### (2) "몇 교시까지 수업하는가"는 별도 테이블로 두지 않는다

시정표에 해당 요일의 교시 행이 존재하는지 여부가 곧 "그 날 몇 교시까지인가"입니다.
수요일 1학년에 1~4교시 행만 있으면 1학년은 수요일 4교시까지입니다.
별도 컬럼을 두면 두 데이터가 어긋날 수 있으므로 단일 출처로 관리합니다.

### (3) 시정표는 "학년별"이 아니라 "프로필 + 학년 매핑"으로 관리한다

학년 6개 × 요일 5개 × 슬롯 8개 = 240행을 손으로 입력하는 건 현실적이지 않습니다.
실제 학교는 보통 2~3개 패턴만 씁니다(저학년 / 중학년 / 고학년).

```
시정표 프로필: [저학년 시정표] [중학년 시정표] [고학년 시정표]
학년 매핑:     1학년→저학년, 2학년→저학년, 3학년→중학년, … 6학년→고학년
```

프로필 1개만 만들어 전 학년에 매핑하면 "학교 전체 하나의 시정표"도 그대로 됩니다.
입력 화면에서는 여전히 "1학년 월요일 5교시는 몇 시?"로 보이게 하고, 저장만 프로필 단위로 합니다.

### (4) 시간은 전부 `자정 기준 분(0~1439) 정수`로 저장한다

`"09:00"` 같은 문자열로 저장하면 비교·차집합·중복 검사에서 반드시 사고가 납니다.
DB에는 `start_min=540, end_min=580`으로 저장하고 화면에서만 `09:00`으로 변환합니다.
겹침 판정도 정수 비교 한 줄로 끝납니다.

### (5) 보결 기록에는 "그때의 실제 시각"을 스냅샷으로 박아 넣는다

학기 중 시정표가 바뀌면 과거 기록의 "5학년 6교시"가 다른 시각을 가리키게 됩니다.
`substitutions` 테이블에 `start_min`, `end_min`, 학년, 반, 교시 라벨을
**비정규화하여 복사 저장**해 과거 기록이 절대 변하지 않도록 합니다.

### 추가로 제안하는 항목 (요구사항에 없지만 필요)

| 항목 | 이유 |
|---|---|
| **결근(부재) 기록 테이블** | A교사가 하루 종일 출장이면 A는 다른 시간 보결 후보에서도 빠져야 합니다. 결근교사 1명만 제외하는 로직으로는 처리 불가 |
| **하루 일괄 보결** | 실제 업무는 "김OO 선생님 내일 하루 연가 → 1~6교시 전부 보결"입니다. 6번 조회는 비효율. 한 화면에서 교시별 추천을 한 번에 보고 배정 |
| **학년도/학기(term) 개념** | 다음 학기에 시간표를 새로 짤 때 기존 데이터를 지우지 않고 세트를 갈아끼움. 과거 통계 보존 |
| **백업/복원** | 로컬 SQLite 단일 파일. PC 교체·고장 대비. 설정 화면에 [백업 파일 내보내기] |

### 1.2 핵심 설계 원칙

**보결 판단 엔진은 Rust `domain/`에 둔다.**

- `cargo test`로 UI 없이 수십 개의 시간 충돌 케이스를 자동 검증 가능.
  이 프로그램에서 가장 틀리면 안 되는 부분이기 때문
- DB·Tauri에 의존하지 않는 순수 함수 → 입력(교사목록, 시정표, 수업, 기존보결)만 주면 결과가 결정됨
- 프론트에서 같은 로직을 재구현할 필요가 없음(중복 구현 = 불일치)

**`domain/`은 DB를 모른다.** `repo/`가 필요한 데이터를 전부 읽어 구조체로 넘기고,
`domain/`은 그것만 보고 계산합니다. 그래서 테스트에서 DB 없이 가짜 데이터로 검증할 수 있습니다.

  id INTEGER PRIMARY KEY,

  name    TEXT NOT NULL,              -- '저학년 시정표'

  id INTEGER PRIMARY KEY,
  bell_schedule_id INTEGER NOT NULL REFERENCES bell_schedules(id) ON DELETE CASCADE,
  day_of_week INTEGER NOT NULL,       -- 1=월 … 5=금

  end_min     INTEGER NOT NULL,
  CHECK (start_min BETWEEN 0 AND 1439),
  CHECK (end_min > start_min),
  CHECK ((slot_type =  'PERIOD' AND period_no IS NOT NULL)
      OR (slot_type <> 'PERIOD' AND period_no IS NULL))

CREATE UNIQUE INDEX ux_bell_period

CREATE INDEX ix_bell_day ON bell_slots(bell_schedule_id, day_of_week);

## 3. 보결 가능 여부 판단 로직 (STEP 1)

### 3.1 시간 표현

```rust
/// 자정 기준 분. 09:00 → 540
pub type Min = i32;

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct Interval { pub start: Min, pub end: Min }   // [start, end)

impl Interval {
    /// 1분이라도 겹치면 true. 접점(09:40 종료 ↔ 09:40 시작)은 겹치지 않음
    pub fn overlaps(&self, o: &Interval) -> bool {
        self.start < o.end && o.start < self.end
    }
}
```

**접점 처리 규칙**: 1교시가 09:40에 끝나고 2교시가 09:40에 시작하면 겹치지 않은 것으로 봅니다.
반열린 구간 `[start, end)`을 쓰면 자동으로 해결됩니다.

### 3.2 교사별 일정(BusyBlock) 생성

특정 **날짜 D**에 대해 각 교사가 바쁜 시간 구간 목록을 만듭니다.

```rust
pub enum BusyKind {
    Lesson,          // 전담/교차 수업
    HomeroomLesson,  // 담임 파생 수업
    Lunch,           // 자기 학년 점심 지도
    FixedDuty,       // 등록된 고정 업무
    Substitution,    // 이미 배정된 보결
    Absence,         // 결근 / 출장
}

pub struct BusyBlock {
    pub teacher_id: i64,
    pub interval:   Interval,
    pub kind:       BusyKind,
    pub label:      String,   // '5-2 영어', '3학년 점심', '이미 보결(4-1 3교시)'
}
```

생성 절차 (요일 W = D의 요일):

1. **직접 수업** — `lessons` where `day_of_week = W`
   → 각 행마다 `class.grade`의 시정표에서 `(W, period_no)` 슬롯을 찾아 `Interval` 획득
2. **담임 파생 수업** (`derive_homeroom_schedule = true`일 때)
   - 각 학급 C: C의 학년 시정표에서 `(W, slot_type='PERIOD')`인 모든 슬롯을 가져옴
   - 그중 `lessons`에 `(C, W, period)` 행이 있는 교시는 **제외** (그 시간은 전담이 담당)
   - 남은 교시 = C의 담임교사가 수업 중인 구간
3. **점심 지도** (`exclude_homeroom_on_own_lunch = true`일 때)
   - 담임교사에게 자기 학급 학년의 `slot_type='LUNCH'` 슬롯을 `Lunch` 블록으로 추가
4. **고정 업무** — `teacher_busy_blocks` where (`WEEKLY` and `day=W`) or (`ONCE` and `date=D`)
5. **기존 보결** — `substitutions` where `date=D` and `status='ASSIGNED'`
   → `sub_teacher_id`에게 `[start_min, end_min)` 블록 추가
6. **결근** — `absences` where `date=D` and `status='ACTIVE'`
   → 종일이면 `[0,1440)`, 시간 단위면 해당 구간

### 3.3 요청 시간 해석

사용자가 고르는 것: **날짜 / 학년 / 반 / 교시(또는 점심)**

```
날짜 2026-09-09 → 요일 = 수(3)
학년 5          → grade_bell_map → '고학년 시정표'
(수, 6교시)     → bell_slots → start_min=830(13:50), end_min=870(14:30)

⇒ 요청 구간 = Interval { start: 830, end: 870 }
```

해당 슬롯이 없으면(예: 수요일 1학년 6교시) 조회를 막고
"1학년은 수요일에 5교시까지 수업합니다. [시정표 설정으로 이동]"을 안내합니다.

### 3.4 후보 필터링 룰 (확장 지점 ①)

```rust
pub struct ExclusionCtx<'a> {
    pub target:       Interval,        // 보결이 필요한 시간
    pub target_class: ClassInfo,       // 대상 학급
    pub date:         NaiveDate,
    pub absent_teacher_id: Option<i64>,
    pub busy:     &'a BusyIndex,       // teacher_id → Vec<BusyBlock>
    pub settings: &'a Settings,
}

pub struct Exclusion { pub rule_key: &'static str, pub message: String }

pub trait ExclusionRule: Send + Sync {
    fn key(&self)   -> &'static str;
    fn label(&self) -> &'static str;
    /// 제외 사유를 반환하면 후보에서 탈락
    fn check(&self, t: &TeacherInfo, ctx: &ExclusionCtx) -> Option<Exclusion>;
}
```

기본 내장 룰:

| rule_key | 내용 | 기본 |
|---|---|---|
| `NOT_SUBSTITUTABLE` | `is_substitutable = 0` | 항상 켬(끌 수 없음) |
| `IS_ABSENT_TEACHER` | 결근 교사 본인 | 항상 켬 |
| `TIME_CONFLICT` | BusyBlock과 1분이라도 겹침 | 항상 켬 |
| `ALREADY_ASSIGNED` | 같은 시간에 이미 다른 보결 | TIME_CONFLICT에 포함, 사유만 구분 표시 |
| `SAME_GRADE_ONLY` | 동학년만 허용 | **꺼짐** (요구사항대로 기본 제한 없음) |
| `MAX_PER_DAY` | 하루 N회 초과 제외 (`params: {max: 2}`) | 꺼짐 |
| `MAX_CONSECUTIVE` | 연속 N교시 초과 제외 | 꺼짐 |

**새 제외 조건 추가 = `ExclusionRule` 구현체 하나 작성 + 레지스트리 등록.** 스키마 변경 없음.

### 3.5 요구사항 시나리오 검증

| 상황 | 처리 |
|---|---|
| 학년별 교시 시간이 다름 | 각 수업의 시각을 **해당 학급 학년의 시정표**에서 조회하므로 자동 해결 |
| 저학년 수업이 일찍 끝남 | 2학년 담임의 마지막 블록이 12:40 종료 → 5학년 6교시(13:50~14:30)와 안 겹침 → **후보** |
| 저·고학년 점심시간이 다름 | 1학년 점심 11:50~12:40, 5학년 점심 13:00~13:50이 각각 별도 블록 |
| 전담교사 공강 | `lessons`에 행이 없는 교시 = 블록 없음 → **후보** |
| 점심 보결 | 요청 구간이 `slot_type='LUNCH'` 슬롯. 나머지 로직 동일 |
| 이미 보결 배정된 교사 | `Substitution` 블록으로 겹침 → 제외 |
| 저학년 담임 → 고학년 보결 | 학년 제한 룰이 기본 꺼짐 → **가능** |

### 3.6 "현재 상태" 라벨 계산

```
그 날 그 교사의 모든 BusyBlock을 시간순 정렬한 뒤,
  - 요청 시간 이후에 남은 블록이 없다 → "수업 종료"
  - 요청 시간 이전에도 블록이 없다   → "수업 없음"
  - 그 외                            → "공강"
```

## 4. 추천 우선순위 정렬 로직 (STEP 2)

### 4.1 룰 인터페이스 (확장 지점 ②)

```rust
pub struct Candidate {
    pub teacher: TeacherInfo,
    pub status:  TeacherStatus,      // 수업종료 | 공강 | 수업없음
    pub count_today: i32,
    pub count_month: i32,
    pub count_total: i32,
    pub homeroom_grade: Option<i32>, // 담임인 경우
    pub homeroom_class: Option<i32>,
    pub subjects: Vec<String>,
    pub last_period_end: Option<Min>,
}

pub trait PriorityRule: Send + Sync {
    fn key(&self)   -> &'static str;
    fn label(&self) -> &'static str;   // 설정 화면에 보일 한국어 이름
    fn hint(&self)  -> &'static str;   // 한 줄 설명

    /// Less = a가 더 앞순위
    fn compare(&self, a: &Candidate, b: &Candidate, ctx: &PriorityCtx) -> Ordering;

    /// 이 룰의 관점에서 이 후보에게 붙일 근거 태그. 해당 없으면 None
    fn tag(&self, c: &Candidate, ctx: &PriorityCtx) -> Option<String>;
}
```

### 4.2 정렬 실행

```rust
let rules: Vec<&dyn PriorityRule> = registry.enabled_in_order(); // DB sort_order 순

candidates.sort_by(|a, b| {
    for r in &rules {
        match r.compare(a, b, &ctx) {
            Ordering::Equal => continue,
            other => return other,
        }
    }
    // 최종 동점 처리: 누적 적은 순 → 이름 가나다순 (결과가 항상 동일하도록 결정적으로)
    a.count_total.cmp(&b.count_total).then(a.teacher.name.cmp(&b.teacher.name))
});
```

**추천 근거 문구**는 두 가지를 합쳐 만듭니다.

1. 활성화된 룰 중 이 후보에게 `tag()`가 붙는 것들 → `동학년`, `전담`, `수업 종료`
2. 바로 아래 순위와 순서를 가른 룰 → 툴팁으로 `"2위보다 이번 달 보결이 1회 적음"`

### 4.3 내장 룰 목록

| rule_key | 라벨 | 비교 기준 | 태그 |
|---|---|---|---|
| `SAME_GRADE` | 동학년 교사 우선 | 담임 학년 == 대상 학년 → 앞 | `동학년` |
| `FEWEST_TODAY` | 당일 보결 적은 순 | `count_today` 오름차순 | `오늘 0회` |
| `FEWEST_MONTH` | 이번 달 보결 적은 순 | `count_month` 오름차순 | — |
| `FEWEST_TOTAL` | 누적 보결 적은 순 | `count_total` 오름차순 | — |
| `PREFER_SPECIAL` | 전담교사 우선 | `role=SPECIAL` → 앞 | `전담` |
| `PREFER_FINISHED` | 수업 종료 교사 우선 | `status=수업종료` → 앞 | `수업 종료` |
| `PREFER_LOWER_GRADE` | 저학년 담임 우선 | 담임 학년 오름차순 | `저학년` |
| `SAME_SUBJECT` | 같은 과목 담당 우선 (확장) | 결시 과목 담당 → 앞 | `과목 일치` |
| `PREFER_ADJACENT` | 인접 교시 근무 중 우선 (확장) | 직전/직후 교시 수업 → 앞 | `연속 교시` |

기본 프리셋(설치 직후): `SAME_GRADE` → `FEWEST_TODAY` → `FEWEST_TOTAL`
설정 화면에서 켜기/끄기 + Drag & Drop 순서 변경 + [기본값으로 되돌리기]

### 4.4 설정 화면의 즉시 미리보기

우선순위를 바꾸면 화면 아래에 **가장 최근 조회 조건으로 재정렬한 결과**를 바로 보여줍니다.
"1순위를 바꾸면 추천이 이렇게 달라집니다"를 눈으로 확인할 수 있게 하여,
설명 없이도 기준을 이해할 수 있게 합니다.

## 8. 확장성 요약

**시간 충돌 판단**

- 모든 시간은 정수 분. 비교는 `Interval::overlaps` 한 곳에서만 수행
- 바쁜 시간의 출처는 `BusyKind`로 구분되지만 형태는 모두 `BusyBlock`으로 동일
  → 새로운 종류의 일정(방과후, 순회, 겸임교 근무 등)이 생겨도
  `BusyBlock` 생성기 하나만 추가하면 충돌 판단 로직은 손대지 않음
- 제외 조건은 `ExclusionRule` 트레이트 구현 + 등록만으로 추가

**학교별 추천 기준**

- 룰의 정의는 코드, 사용 여부·순서·파라미터는 DB
- 새 기준 추가 = `PriorityRule` 구현 + 레지스트리 등록. 스키마 변경 없음
- 기존 학교의 설정은 `rule_key` 기준으로 보존되므로 업데이트 후에도 그대로 동작
